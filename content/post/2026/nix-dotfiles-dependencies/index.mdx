シェルのプラグインや CLI ツールのパッケージ管理は、依存関係の解決がずっと大変だった。[enhancd](https://github.com/babarot/enhancd) は fzf がないと動かないし、自作の関数やエイリアスも、中でいろいろなコマンドを呼んでいる。どれかを消したり、新しい Mac で入れ忘れたりすると、それを使っている別のものが壊れる。しかも壊れたことに気づくのは、使おうとしたときだ。

10年以上 dotfiles をいじってきて、この問題には何度もやり方を変えて向き合ってきた。そして[前回の記事](/post/2026/10/01/ai-agent-first-dotfiles/)で書いたとおり、今は Nix（nix-darwin と home-manager）で管理している。使ってみて、自分がパッケージ管理に求めていたのはこれだったと思った。今回は、Nix で依存関係をどう解決しているかを書く。

## これまでの依存の解決

### `$+commands` で存在を確かめる

いちばん素朴なのは、使う前にコマンドがあるかを確かめるやり方だ。zsh の `$+commands[name]` は、そのコマンドが PATH にあれば1になる（`which` で確かめるのとだいたい同じ）。昔の `.zshrc` には、こういう行がたくさんあった。

```zsh:.zsh/30_aliases.zsh
if (( $+commands[kubectl] )); then
  alias k=kubectl
fi

if (( $+commands[nvim] )); then
  alias vim=nvim
fi
```

これで、ないコマンドのせいでエラーになることはなくなる。ただ、やっているのは「なければ使わない」だけで、依存を解決しているわけではない。kubectl を入れ忘れれば `k` は黙って使えなくなるし、そもそも kubectl をどこで入れているかは、この行を見てもわからない。

### zplug で依存を宣言する

次に、zsh のプラグインマネージャの [zplug](https://github.com/zplug/zplug) を作った。zplug では、パッケージごとに `on:` で依存するパッケージを、`if:` で読み込む条件を書ける。2016年ごろの設定はこうなっていた。

```zsh:.zsh/zplug.zsh
zplug "b4b4r07/emoji-cli", \
    if:'(( $+commands[jq] ))' \
    on:"junegunn/fzf-bin"
```

emoji-cli は fzf と jq を使うので、fzf は `on:` で zplug が入れるパッケージへの依存として書き、zplug の外で入れている jq は `if:` で存在を確かめている。依存を設定に書けるようになったのは前進だったが、結局 zplug が管理していないものは `$+commands` に頼るしかなかった。

### afx で依存を宣言する

その後、zplug の考え方を引き継いで、プラグインもコマンドも YAML で管理する [afx](https://github.com/babarot/afx) を作った。afx には `depends-on` があり、パッケージ同士の依存を書くと、`afx init` がそれに合わせて読み込む順番を並べ替える。

```yaml:~/.config/afx/github.yaml
- name: olets/zsh-abbr
  owner: olets
  repo: zsh-abbr
  depends-on:
  - olets/zsh-job-queue
  plugin:
    sources:
    - zsh-abbr.zsh
```

ここでも、afx の外にあるコマンドへの依存は、`if:` に `$+commands` を書いて解決していた。zplug のときの emoji-cli なら、afx ではこうなる。

```yaml:~/.config/afx/github.yaml
- name: b4b4r07/emoji-cli
  owner: b4b4r07
  repo: emoji-cli
  depends-on:
  - junegunn/fzf
  plugin:
    if: |
      (( $+commands[jq] ))
    sources:
    - emoji-cli.zsh
```

書き方が YAML になっただけで、やっていることは zplug と変わらない。

振り返ると、どのやり方も、依存しているのは「PATH にある、その名前のコマンド」だった。誰がそれを入れたのか、どのバージョンなのかは知らないし、消されたら壊れるか、黙って使えなくなるだけだ。`depends-on` も読み込む順番を決めてくれるだけで、依存先が消えるのを止めてはくれない。

## Nix で何が変わったか

### Nix とは

[Nix](https://nixos.org/) は、パッケージを「入力から決まる出力」として扱うパッケージマネージャだ。パッケージのビルドに使うもの（ソース、コンパイラ、依存するライブラリやコマンド、ビルドの手順）を全部宣言して、それをもとにビルドする。同じ入力からは同じものができる、という関数のような考え方で、マニュアルでも purely functional なパッケージマネージャと名乗っている。

ビルドしたものは `/nix/store/` の下に、入力から計算したハッシュを名前に付けて置かれる。これを store と呼ぶ。

```
/nix/store/b5jbljds0rvgj4vxdcg903gj03bfk63x-fzf-0.74.4/bin/fzf
```

入力が1つでも変われば別のハッシュの別の場所になるので、一度置いたものを上書きすることはない。同じパッケージのバージョン違いも、別々の場所に並んで置ける。更新すると古いものが新しいものに入れ替わる、ということがない。

### 依存も store のパスで持つ

この store の上で、パッケージは依存するものを名前ではなく store のパスで指す。例えば nixpkgs の bat は、ページャに使う less を store のパスで参照している。`nix-store -q --references` で bat が参照している store のパスを見ると、こうなる。

```console
$ nix-store -q --references /nix/store/n65zrzg7x0kv5mxr1y4wg0xsjmkiy4z4-bat-0.26.1
/nix/store/3yn3dx5fwg5i0inqqzwnxq7f6lwhpjqa-less-710
/nix/store/f0b9dbw2gl596cm03pvdsss72381qhlp-bash-5.3p15
/nix/store/fgrxz4hr8f71hkhsddbvk8nxadpg67bv-libiconv-115.100.1
/nix/store/n65zrzg7x0kv5mxr1y4wg0xsjmkiy4z4-bat-0.26.1
```

Nix はこの参照を自分で記録している。パッケージと、それが参照するものを全部まとめたものを closure と呼び、bat を入れれば less も含めた closure が丸ごと揃う。逆に、ガベージコレクション（`nix-collect-garbage`）で消されるのは、どこからも参照されなくなった store のパスだけだ。参照されている限り消えないので、入れたはずの依存がない、ということが起きない。

### PATH はプロファイルが作る

では、ふだん `fzf` と打って動くのはなぜか。PATH には store を直接並べるのではなく、プロファイルというディレクトリ（`/etc/profiles/per-user/babarot/bin` など）を入れていて、そこに store の本体へのリンクが並んでいる。home-manager で「パッケージを入れる」というのは、このリンクを作ることだ。消すときもリンクを外すだけで、本体は store に残る。

### 設定も store のパスを持てる

ここまではパッケージの話だが、home-manager ではシェルの設定ファイルも Nix が生成する。そして `.nix` の中で `lib.getExe pkgs.fzf` と書くと、fzf の store のパス（`/nix/store/…-fzf-0.74.4/bin/fzf`）が文字列として取れる。これを生成する設定ファイルに埋め込むと、Nix はパッケージのときと同じように、「この設定ファイルは fzf を参照している」と記録してくれる（文字列が、自分の中にある store のパスを覚えている。string context と呼ばれる仕組み）。

つまり自分の dotfiles の設定も、nixpkgs の bat が less を持つのと同じやり方で、依存を持てる。シェルの関数から fzf を名前で呼ぶ場合と、store のパスで呼ぶ場合を並べるとこうなる。

名前で呼ぶほうは、PATH 上のリンクがあることが前提で、リンクを外せば届かなくなる。store のパスで呼ぶほうは、PATH に誰が何を載せているかとは関係なく、自分が使う fzf を直接指す。その fzf は、参照されている限り消えない。`$+commands` で確かめる必要も、読み込む順番を気にする必要もなくなった。

これをどう使っているかを、今の dotfiles で説明する。

## babarot/dotfiles ではどう書いているか

自分の dotfiles（[babarot/dotfiles](https://github.com/babarot/dotfiles)）は nix-darwin と home-manager で書いている。nix-darwin は macOS のシステムの設定を、home-manager はユーザーのホームディレクトリ（入れるパッケージや、`~/.config` の下の設定ファイル）を Nix で宣言するためのもので、私用と仕事用の Mac 2台を1つの flake で管理している。

書くのは `.nix` ファイルで、中身は「何を入れて、どんな設定を生成するか」の宣言だ。例えば eza のファイルはこうなっている（抜粋）。

```nix:nix/home-manager/tools/eza.nix
{ pkgs, ... }:
{
  home.packages = [ pkgs.eza ];

  my.human.aliases = {
    ls = "eza --group-directories-first";
    ll = "eza --group-directories-first -l --header --git";
    # ...
  };
}
```

`home.packages` に書いたパッケージは、さっきのプロファイルにリンクされて PATH に載る。`my.human.aliases` は自分で作った option で、ここに書いたエイリアスは人間用のシェルが読む `human.zsh` に書き出される（option はあとでまとめて書く）。`darwin-rebuild switch` を実行すると、Nix がパッケージを store に揃え、プロファイルと設定ファイルを作り直す。

こういうファイルが `nix/home-manager/tools/` に並んでいて、全部自動で読み込まれる。一覧をどこかに書く必要はない。

```nix:nix/home-manager/default.nix
imports = [
  ./dotfiles.nix
  ./env.nix
  ./git.nix
  ./human.nix
  ./ai.nix
  # ...
]
++ map (f: ./tools + "/${f}") (
  builtins.filter (f: builtins.match ".*\\.nix" f != null) (
    builtins.attrNames (builtins.readDir ./tools)
  )
);
```

### 1ツールごとに1ファイル

ファイルは、1ツールごとに1つ作るのが基本だ（[前回の記事](/post/2026/10/01/ai-agent-first-dotfiles/)で「1ツール1ファイル」と呼んだもの）。そのうえで、一緒に入れて一緒に消すべきものは、1つのファイルに組む。ファイルを置けば中のものが全部入って設定され、消せば全部消える。そして、まだ使っているものは消えない。ほとんどのファイルは1つのツールだが、それだけでは収まらないものもあるので、ファイルを4種類に分けている。

| 種類 | ファイル名 | 中身 | 例 |
|---|---|---|---|
| ツール | `<tool>.nix` | 1つのツールとその設定 | `eza.nix`、`gomi.nix` |
| メインとヘルパー | `<メインのツール>.nix` | メインのツールと、それを助けるためだけにあるヘルパー | `gh.nix`（gh-dash が使う delta と lazygit）、`neovim.nix`（LSP サーバーとフォーマッタ） |
| グループ | `<対象>.group.nix` | メインのいない、1つの対象のためのツール | `kubernetes.group.nix` |
| カタログ | 決まった名前 | 設定のないツールやアプリの一覧 | `packages.nix`、`apps.nix` |

4つを図にするとこうなる。

<Partial name="file-kinds" />

メインとヘルパーは「メインを消すなら、ヘルパーも全部消していい。逆は成り立たない（ヘルパーを消してもメインは残る）」という関係だ。delta と lazygit は gh-dash から呼ぶために入れているので、gh を消すなら一緒に消していい。一方、fzf は bat の関数の中で使われているが、bat を消しても fzf は残したい。なので fzf は bat のヘルパーではなく、自分のファイル（`fzf.nix`）を持つ独立したツールになる。依存されているかどうかと、ヘルパーかどうかは別の話で、この区別があとで書く依存の持ち方にそのまま効いてくる。

グループは「その対象を使わなくなるときに、全部まとめて消していい」ものの集まりだ。例えば Kubernetes まわりのツール（kubectl、kubectx、helmfile、krew など）は、Kubernetes を触らなくなれば全部いらなくなるので、`kubernetes.group.nix` にまとめている。逆に、linter、フォーマッタ、JSON や YAML を扱うツールのように、種類が同じなだけのものはグループにしない。それぞれ別々に足したり消したりするので、1つのファイルにまとめると、ファイルを消したときにまだ使っているツールまで消えてしまう。グループのファイル名に `.group` を付けているのは、`kubernetes.nix` だと kubernetes というツールのファイルに見えてしまうからだ。

1台の Mac でしか使わないものは、同じ形のファイルを `nix/hosts/<host>/` に置き、その Mac にだけ読み込ませている。Kubernetes のグループも、仕事用の Mac のディレクトリにある。

### ファイルに書く設定

どの種類のファイルにも、パッケージと一緒にそのツールのための設定を書く。書き先として、home-manager の上にいくつか自前の option を作っている。

| option | 書くもの | 出力先 |
|---|---|---|
| `my.human` | 人間だけのエイリアス、関数、環境変数、zsh プラグイン | `~/.config/zsh/human.zsh` |
| `my.ai` | AI だけの環境変数とエイリアス | `~/.config/zsh/ai.zsh` |
| `my.env` | 人間にも AI にも要る環境変数（`GOPATH` など） | `~/.config/zsh/env.zsh` |
| `my.path` | そのツールだけが必要とする PATH のディレクトリ | `~/.config/zsh/env.zsh` |
| `my.gitConfig` | そのツールを使う git の設定 | `~/.config/git/tools.gitconfig` |
| `my.skills` | ツールに同梱の Agent Skill | `~/.claude/skills` など |

どれもツールのファイルから書けて、Nix のモジュールの仕組みで1つのファイルにまとめて出力される。`my.human` と `my.ai` の使い分けは[前回の記事](/post/2026/10/01/ai-agent-first-dotfiles/)で書いたので、今回は残りの `my.path` と `my.gitConfig`、そしてそもそもの依存の持ち方を書く。

## PATH に載せるのは自分のツールだけ

ファイルを消せば、中のツールもエイリアスも環境変数も一緒に消える。ただ、ツールは自分のファイルの中だけで使われているとは限らない。例えば bat には、テーマを fzf で選びながらプレビューする `bat-theme` という関数を生やしている。さっき書いたとおり fzf は bat のヘルパーではなく、`fzf.nix` を持つ独立したツールだ。この関数が `fzf` と名前で呼んでいたら、`fzf.nix` を消した時点で `command not found` で落ちる。しかもビルドは普通に通る。`$+commands` の時代と同じ問題だ。

なので bat は、実際にはこう書いている。

```nix:nix/home-manager/tools/bat.nix
{ lib, pkgs, ... }:
let
  # Used inside bat-theme only; fzf on PATH is fzf.nix's
  fzf = lib.getExe pkgs.fzf;
in
{
  home.packages = [ pkgs.bat ];

  my.human.env = {
    BAT_PAGER = "less -RF";
    BAT_STYLE = "numbers,changes";
    BAT_THEME = "DarkNeon";
  };

  # Agents read bat's output, not scroll it
  my.ai.env.BAT_PAGER = "cat";

  my.human.init = ''
    bat-theme() {
      local file=$1
      if [[ -z $file ]]; then
        file=$(${fzf})
      fi
      bat --list-themes | ${fzf} --preview="bat --theme={} --color=always ''${file}"
    }
  '';
}
```

この1ファイルに、bat を入れること、人間と AI で違うページャ、`bat-theme` 関数が全部入っている。肝となるのは `bat-theme` の中の fzf で、`fzf` と名前で呼ばずに `${fzf}`、つまり `lib.getExe pkgs.fzf` で取った store のパスを埋め込んでいる。生成される `human.zsh` には `/nix/store/b5jb…-fzf-0.74.4/bin/fzf` のようなパスがそのまま書かれる。

決まりとしてはこうだ。`home.packages` で PATH に載せるのは、そのファイルのツール（とそのヘルパー）だけ。ほかのツールの設定の中で使うコマンドは、PATH を通さずに store のパスで呼ぶ。fzf を PATH に載せるのは `fzf.nix` の仕事で、bat は fzf が PATH にあるかどうかを気にしない。

同じ fzf でも、呼び方によって依存の性質がまるで違う。

| | PATH 経由 | store のパス経由 |
|---|---|---|
| 書き方 | 関数の中で `fzf` と名前で呼ぶ | `${lib.getExe pkgs.fzf}` を埋め込む |
| Nix はこの依存を知っているか | 知らない | 知っている（closure に入る） |
| `fzf.nix` を消すと | 実行時に壊れる | そのまま動く |

### fzf.nix を消すとどうなるか

ここで、さっきの Nix の仕組みがそのまま効く。`fzf.nix` を消して switch しても、外れるのはプロファイルの `bin/fzf` のリンクだけだ。一方、`bat.nix` が書き出す `human.zsh` には fzf の store のパスが入っていて、Nix はその参照を記録しているので、fzf の本体は closure に残る。依存を持っているのは使う側のファイル自身なので、PATH に誰が何を載せているかとは関係なく動く。

実際に `fzf.nix` を一時的に消してビルドし、生成物を見てみた。プロファイルの `bin/fzf` はなくなり、`fzf.nix` に書いていた `pskill`（fzf でプロセスを選んで kill する関数）も消えた。一方で、`bat-theme`、gcloud の関数、enhancd のフィルタ、fzf-tab は、store の fzf を指したまま残っていた。fzf を消したら fzf だけが消える、という狙いどおりの結果になった。

### 書き方

シェルの関数や環境変数の中で使うなら、`let` で store のパスを取っておいて埋め込むだけだ。zsh のプラグインなら、プラグインが呼ぶコマンドを設定で指定できることが多い。fzf-tab は `zstyle` で fzf のコマンドを渡せる。

```nix:nix/home-manager/tools/fzf-tab.nix
# fzf from the store, so it does not depend on fzf.nix putting fzf on PATH
zstyle ':fzf-tab:*' fzf-command ${lib.getExe pkgs.fzf}
```

[enhancd](https://github.com/babarot/enhancd) は、フィルタとそのプレビューに使う eza の両方を store のパスで持っている。

```nix:nix/home-manager/tools/enhancd.nix
let
  # The filter and its preview, by store path: enhancd does not depend on
  # fzf.nix or eza.nix putting them on PATH
  fzf = lib.getExe pkgs.fzf;
  eza = lib.getExe pkgs.eza;
in
{
  my.human.env.ENHANCD_FILTER = lib.concatStringsSep " " [
    "${fzf} --preview '${eza} -al --tree --level 1 --group-directories-first --git-ignore"
    # ...
  ];
}
```

`gcloud.nix` も同じで、configuration を fzf で切り替える `gchange` や、切れた認証だけログインし直す `ohayo` が使う fzf と gum を store のパスで呼んでいる。`gcloud.nix` を消せば gcloud と一緒にこれらの関数も消えるし、`fzf.nix` や gum を消してもこれらは壊れない。

ちなみに、別のファイルが同じ `pkgs.fzf` を参照していても、store のパスは同じなので fzf が2つ入ることはない。`home.packages` も同じで、各ファイルのリストはモジュールの仕組みで1本につながれ、同じパッケージが何回出てきても入るのは1つだ。重複を気にして入れる場所を1か所に寄せる必要はなく、気にするべきなのは「PATH に載せる責任を誰が持つか」のほうだと思う。

### Neovim は自分だけの PATH を持つ

シェル関数なら1か所ずつ store のパスを埋め込めばいいが、エディタは中でたくさんのコマンドを名前で呼ぶ。Neovim の LSP の設定（`vim.lsp.enable`）は gopls や lua-language-server を PATH から探すし、保存時に整形する conform は goimports や jq、shfmt を PATH から呼ぶ。これらを全部ユーザーの PATH に頼っていると、例えば `jq.nix` を消しただけで、nvim の JSON の整形が黙って動かなくなる。

LSP サーバーとフォーマッタは nvim のためにあるので、nvim のヘルパーとして `neovim.nix` に書いている。ただ、そのまま `home.packages` に入れると、nvim しか使わないものがユーザーの PATH に並ぶ。jq のように自分のファイルを持つツールも混ざっている。Lua の設定に store のパスを書くこともできるが、手書きの Lua に Nix の値を埋め込むのはめんどくさい。そこで nvim 自体を包んで、nvim だけの PATH にこれらを足している。

```nix:nix/home-manager/tools/neovim.nix
  # Tools only Neovim runs: LSP servers and conform's formatters. They go
  # on nvim's own PATH, not the user's, so deleting jq.nix or go.nix does
  # not break formatting in nvim. Appended, so a version a project pins
  # with mise still wins.
  tools = with pkgs; [
    gopls
    lua-language-server
    terraform-ls
    go # gofmt
    gotools # goimports
    jq
    shfmt
    terraform
  ];
  neovim = pkgs.symlinkJoin {
    name = "neovim-with-tools";
    paths = [ pkgs.neovim ];
    nativeBuildInputs = [ pkgs.makeWrapper ];
    postBuild = ''
      wrapProgram $out/bin/nvim --suffix PATH : ${lib.makeBinPath tools}
    '';
  };
in
{
  home.packages = [ neovim ];
```

`wrapProgram` は、`bin/nvim` を「PATH を足してから本物の nvim を起動する」小さなスクリプトに置き換える。足しているのは store のパスなので、考え方はシェル関数の `${fzf}` と同じだ。ポイントは2つある。

- `--suffix` で PATH の末尾に足すので、プロジェクトが mise で別のバージョンの gopls などを指定していれば、そちらが先に見つかる
- `home.packages` に入るのは包んだ nvim だけで、gopls などの LSP サーバーはユーザーの PATH に出てこない。nvim しか使わないものが、ユーザーの PATH に並ばなくなる

試しに PATH を `/usr/bin:/bin` だけにして nvim を起動してみると、8つのツールがすべて見つかり、崩した JSON を conform が jq で整形した。シェル関数は1か所ずつ埋め込み、中でたくさんのコマンドを名前で呼ぶものはプログラムごと包む。形は違うが、どちらも依存を store のパスで持っていることに変わりはない。

### 例外

全部を store のパスにしているわけではない。次の3つは PATH のままにしている。

- macOS 標準のコマンドと git（awk、sed など）: 消えたら何もかも壊れるので、store のパスにする意味がない
- 手書きの設定ファイルの中で使うもの: gh-dash の `config.yml` は delta と lazygit を呼ぶが、このファイルには store のパスを書けない。delta と lazygit は gh-dash のためだけにあるので、gh のヘルパーとして `gh.nix` が PATH に載せている
- あれば使う、という任意の利用: `$+commands[gh]` で存在を確かめてから使うようなもの

この決まりは dotfiles の AGENTS.md の「Where things go」にも書いてある。今は dotfiles をいじるのもほとんど AI なので、AI がツールを足すときもこれに従ってくれる。

## ほかのプログラムの設定に参加する

ここまでは「ほかのツールを中で使う」話だった。逆向きに、ツールのファイルから、PATH や git のような別のプログラムの設定に参加したいこともある。これも、設定をツールのファイルに書いておけば、ツールと一緒に消える。

### my.path

PATH の順番は、どれか1つのツールのものではないので、`.zshenv` に手で書いている。mise の shims、`~/bin`、Nix のプロファイル、Homebrew の順だ。順番が大事なので、ツールのファイルからは触らせない。

ただ、「このツールだけが必要とするディレクトリ」まで `.zshenv` に書くと、ツールを消したときに PATH の行だけが取り残される。そこで `my.path` を作った。ツールのファイルに書いたディレクトリは、`env.zsh` でこう出力される。

```nix:nix/home-manager/env.nix
config.xdg.configFile."zsh/env.zsh".text = lib.concatLines (
  [ "# Generated by nix/home-manager/env.nix. Do not edit." ]
  ++ lib.mapAttrsToList (k: v: "export ${k}=${sh v}") config.my.env
  ++ map (d: "if [[ -d ${sh d} ]]; then path+=(${sh d}); fi") config.my.path
);
```

`path+=` なので、手書きの順番は崩さず PATH の末尾に足すだけだ。ディレクトリがなければ何もしない。リストなので、いくつのファイルから足してもいい（`my.env.PATH` に書くと値の置き換えになり、2つのファイルで書くと評価エラーになる）。

<Partial name="path-order" />

使っている例はこのあたり。

- Go: `go install` の出力先を `GOBIN=~/go/bin` にして、`go.nix` の `my.path` で末尾に足している。`GOPATH=$HOME` のままだと出力先が `~/bin` になり、PATH の先頭なので、エディタのプラグインが更新のたびに入れ直す golangci-lint などが Nix 版を隠してしまう。末尾にあれば Nix 版が必ず勝つ
- OrbStack: OrbStack は自分で `~/.zprofile` を作って PATH を足す（ログインシェルにしか効かない）。cask を宣言しているホストのファイルの隣に `my.path` を置いて、`.zprofile` は消した
- krew: kubectl のプラグインは `~/.krew/bin` に入る。Kubernetes のグループに、krew と並べて `my.path` を書いている

```nix:nix/home-manager/tools/go.nix
{ config, pkgs, ... }:
let
  gobin = "${config.home.homeDirectory}/go/bin";
in
{
  home.packages = [
    pkgs.go
    # ...
  ];

  my.env.GOPATH = config.home.homeDirectory;
  my.env.GOBIN = gobin;
  my.path = [ gobin ];
}
```

グループのファイルでも同じだ。Kubernetes のグループは、パッケージと一緒に krew の `my.path` を持っているので、グループを消せば PATH の行も消える。

```nix:nix/hosts/<host>/kubernetes.group.nix
# Group: tools for working with Kubernetes clusters, on the work Mac only.
# A new Kubernetes tool goes in this file, not in a file of its own; see
# "One file, one unit" in AGENTS.md for what makes a group.
{ config, pkgs, ... }:
{
  home.packages = with pkgs; [
    helmfile
    kail
    krew
    kubectl
    # ...
  ];

  # krew installs kubectl plugins here as kubectl-* commands
  my.path = [ "${config.home.homeDirectory}/.krew/bin" ];

  my.human.plugins.zsh-abbr.init = ''
    abbr --session --quiet k=kubectl
  '';
}
```

### my.gitConfig

git の設定にも、ツールに属するものがある。git の log と show のページャを [ov](https://github.com/noborus/ov) にする設定や、[difftastic](https://github.com/Wilfred/difftastic) で diff を見る `git dft` のエイリアスだ。これらを手書きの `.gitconfig` に書くと、ツールを消したときに設定だけが残り、git がないコマンドを呼んで失敗する。

そこで `my.gitConfig` を作った。ツールのファイルに、store のパス付きで git の設定を書く。

```nix:nix/home-manager/tools/ov.nix
# ov: pager for `git log` / `git show`
{ lib, pkgs, ... }:
let
  ov = lib.getExe pkgs.ov;
in
{
  home.packages = [ pkgs.ov ];

  my.gitConfig.pager = {
    log = "${ov} -F --section-delimiter '^commit' --section-header-num 3";
    show = "${ov} -F --header 3";
  };
}
```

```nix:nix/home-manager/tools/difftastic.nix
{ lib, pkgs, ... }:
{
  home.packages = [ pkgs.difftastic ];

  my.gitConfig.alias.dft = "-c diff.external='${lib.getExe pkgs.difftastic} --syntax-highlight=off' diff";
}
```

書いたものは `~/.config/git/tools.gitconfig` にまとめて出力され、手書きの `.gitconfig` は最後にそれを include するだけだ。

```ini:home/.gitconfig
# Settings that belong to a tool (ov as the pager, the dft alias), written
# with store paths in its nix/home-manager/tools/<tool>.nix (my.gitConfig).
# Last, so they win over anything above
[include]
  path = ~/.config/git/tools.gitconfig
```

`ov.nix` を消せば `tools.gitconfig` から ov の行が消え、ページャは `core.pager` の less に戻る。git は include したファイルが空でも、なくてもエラーにしないので、全部のツールを消しても困らない。`my.path` と同じく、ツールのファイルから別のプログラムの設定に参加して、消すときは一緒に消える形になっている。

## パッケージが余計なコマンドまで PATH に出す

PATH に載せるのは自分のツールだけ、と書いたが、これはパッケージの単位で考えると少しずれる。nixpkgs のパッケージは、思っていない名前のコマンドも一緒に入れることがあるからだ。実際に引っかかったのはこの3つ。

- `pkgs.gawk` は gawk だけでなく `bin/awk` も入れる。PATH で macOS の BSD awk より先に来るので、AI が書く BSD 前提のコマンドの挙動が変わってしまう
- `pkgs.gotools` は50個ほどのコマンドを入れ、その中の `bundle` が Ruby の bundle を隠していた
- `pkgs.bashInteractive` は `bin/sh` も入れるので、macOS の `/bin/sh` より先に来ていた

どれも、欲しいコマンドだけをリンクしたパッケージを作って直した。

```nix:nix/home-manager/tools/bash.nix
# A current bash for scripts that run `#!/usr/bin/env bash`. Only bash is
# linked: bashInteractive also ships bin/sh, which would come before
# macOS's /bin/sh on PATH.
{ pkgs, ... }:
{
  home.packages = [
    (pkgs.runCommand "bash" { } ''
      mkdir -p $out/bin
      ln -s ${pkgs.bashInteractive}/bin/bash $out/bin/bash
    '')
  ];
}
```

gawk と goimports も同じ形だ。確かめ方は `which -a awk` で先頭が何かを見るだけなのだが、困ったことに、何かがおかしくなるまで見ようと思わない。[前回の記事](/post/2026/10/01/ai-agent-first-dotfiles/)で書いたとおり、AI は macOS にいることをわかっていて BSD の書き方をしてくるので、こういう名前の衝突は人間より AI の方が先に踏みやすいと思う。

## ほかのやり方

依存の持ち方には、ほかにも2つのやり方がある。

1. fzf を入れるのは `fzf.nix` だけにして、ほかは PATH の fzf を使う
2. 使う側のファイルが全部 `pkgs.fzf` を `home.packages` に入れる

1はいちばんシンプルだ。fzf を消すときは使っている側も一緒に見直す、と割り切れるならこれで十分だと思う。ただ、消したファイル以外がビルドを通ったまま壊れるし、どこで fzf を使っているかを覚えておく必要がある。

2なら `fzf.nix` を消しても動く。ただ、使う側が fzf を PATH に載せてしまうので、`fzf.nix` を消しても `fzf` が打てるままになる。「fzf を PATH に載せるのは `fzf.nix`」があいまいになり、ファイルを消したのにツールが消えない、という、一緒に入れて一緒に消すものでファイルを組んだ意味がなくなる。とはいえ、手書きの設定ファイルから呼ばれるもの（gh-dash の delta など）はこの形しかとれないので、ヘルパーとしてメインのツールのファイルに入れている。

## おわりに

`$+commands` で存在を確かめていたころから、zplug、afx と、依存はいつも「PATH にあるはずの名前」だった。Nix にしてはじめて、依存を自分で持てるようになった。PATH に載せる責任と、中で使う依存を分けて、後者を store のパスで持つ。これだけで、ファイルを1つ消したときに何が起きるかが、そのファイルを見ただけでわかるようになった。10年かけてやっと、求めていたパッケージ管理にたどり着いた気がする。

もちろん課題もある。手で入れたアプリや、アプリが勝手に書くファイル（OrbStack の `.zprofile` のようなもの）は、宣言されないまま残る。これはときどき棚卸しするしかなさそうだ。手書きのシェルスクリプトを `writeShellApplication` で配って、`runtimeInputs` で依存を持たせるのもまだやっていない。このあたりはしばらく使いながら決めていくと思う。
